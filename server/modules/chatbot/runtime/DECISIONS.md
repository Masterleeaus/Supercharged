# Runtime decisions (conversation and reply runtime)

Each entry: date, decision, reason. Behaviour-changing items are also for the checklist.

- 2026-11-08. Reply events go to an injected sink, not the inbox EventPublisher. The inbox publisher only accepts its own event types. The outbox agent owns delivery. Reason: avoid a second realtime path.
- 2026-11-08. Replies are stored through the existing ChatbotService.recordAssistantReply, which runs the generative-UI composer. The runtime does not repeat composition. Composer instructions are added to the prompt only when the chatbot has generativeUiEnabled and the request matches shouldGenerate.
- 2026-11-08. One stored reply per customer message. A turn claim (company, conversation, turn key) is taken before any model call. Default key is "msg:<latest customer message id>". Reason: the PHP had no such guard. Concurrent or repeated calls now return duplicate or in_progress.
- 2026-11-08. Pending claims are leases (default 120 s). A crashed worker's claim is taken over after the lease. Reason: avoid a permanent block.
- 2026-11-08. A failed generation releases the claim, so a retry can store the reply. Failure reasons are codes only (provider_error:<code>, empty_reply, stream_error, internal_error). Raw provider messages are never returned. Reason: provider messages may echo request data.
- 2026-11-08. Knowledge retrieval runs only when CHATBOT_KNOWLEDGE_ENABLED is exactly "true" (readFlag). A retrieval error gives a reply with no reference text. Reason: a search outage should not block customers.
- 2026-11-08. Reference knowledge is wrapped in explicit markers and described as data, not instructions. Marker text inside chunks is removed. Chunks are ordered by score and capped at 6000 characters by default.
- 2026-11-08. History excludes internal notes and any role other than user or assistant. Last 20 messages by default.
- 2026-11-08. Failover uses the registry order passed in. Only retryable ModelProviderError values move to the next provider. Each provider needs a model id in options. Providers with no model id are skipped.
- 2026-11-08. Streaming uses the first usable provider only. No failover after the stream starts. Reason: contract forbids failover after the first delta.
- 2026-11-08. Streaming persists the full text once, at the end, through persistReply. A stream error or a persist error sends an error frame and stores nothing. Partial text already sent to the client is not retracted. Reason: the PHP persisted every event for replay, which is not ported here.
- 2026-11-08. Stream frames are sequenced per reply (1, 2, 3 ...). Typing frames have no sequence. No transport is named. Publish failures are swallowed.
- 2026-11-08. Stream replay table (ext_chatbot_stream_events) is not ported. Reason: no transport is chosen yet.
- 2026-11-08. Draft runtime returns text only and has no send or insert dependency. Confidence is always null. The model reports none that can be trusted. Reason: contract says model confidence is not trusted.
- 2026-11-08. Draft context carries no chatbot title. The draft system prompt says "for this business" in that case.
- 2026-11-08. translate returns the original text when no provider is usable or the reply is empty. Same as the PHP fallback.
- 2026-11-08. Summary is a pure function of the transcript. Caching and summary_updated_at are now implemented in conversation-runtime.ts (updated 2026-11-09). The reason given was that chatbot storage has no summary column; that column now exists in shared/schema.ts (updated 2026-11-09). ConversationRuntime.create, archive, merge and search are now implemented in conversation-runtime.ts (updated 2026-11-09). The merge storage change request is done (updated 2026-11-09).
  - 2026-11-09 note: this 2026-11-08 entry is superseded in part by the 2026-11-09 entries (Summary cache, Merge rules, Conversation runtime gaps). The decision itself stands as history: summary is still a pure function of the transcript, and caching now sits on top of it.
- 2026-11-08. Summary strips tags with a simple regex, not PHP strip_tags. Fallback truncates by code point, 1200 characters.
- 2026-11-08. Staff drafts (PHP DraftRuntime save/get/delete) are kept, keyed by (company, conversation, staff). A null staff id is stored as ''. Reason: nullable uniqueness.
- 2026-11-08. Migration number 0050 is reserved for this slice in db/migrations-draft/. Other slices may need a different number. Owner to confirm at promotion.
- 2026-11-08. Flags: no new flag added. Contracts state new flags go in flags.ts, which this slice may not edit. Only KNOWLEDGE_ENABLED is read.
- 2026-11-08. Delivery status rules (MessageRuntime.php rank table) are pure functions in delivery-rules.ts. Nothing is persisted: chatbot storage has no delivery_status column. Receipts and outbox events are not ported (outbox is another agent's).

## Conversation runtime gaps (2026-11-09)

Files: conversation-store.ts (storage port and memory store), conversation-runtime.ts (create, archive, merge, search, summarize), delivery-status.ts (sent, delivered, failed, retry, with compare-and-set), summary.ts (summarizeWithStatus added; summarizeConversation unchanged in result). Tests: tests/modules/chatbot-runtime-conversations.test.mjs.

- 2026-11-09. Archive sets status "archived" and keeps every row and message. Archive of an already-archived or merged conversation returns it unchanged and writes no event. Reason: archive hides without deleting, and repeats must not add events.
- 2026-11-09. Search with no status filter returns only "open" conversations. Pass "archived" or "merged" to see those. Reason: archived and merged rows must stay out of the default list. The contract does not state this default; it is a decision to review.
- 2026-11-09. Search cursor is opaque base64url of (updatedAt, id), ordered newest first. Limit is clamped to 1 to 100, default 25. Query text is trimmed and capped at 200 characters. A malformed cursor throws invalid_cursor.
- 2026-11-09. Merge rules: source and target must be in the company (else null, nothing moved). Same id throws self_merge. Different chatbot throws chatbot_mismatch. Target must be open (else target_not_open). Source already merged elsewhere throws source_merged_elsewhere. Repeating the same merge returns the target and moves nothing. Reason: merge moves messages once and never across companies.
- 2026-11-09. Merge moves messages, marks the source merged with mergedIntoId, and writes one outbox row, as one store call. The contract does not describe error behaviour; errors are thrown as ConversationRuntimeError with a code only.
- 2026-11-09. Create uses handler "ai" and throws chatbot_not_found when the chatbot is not in the company. Reason: the same error as absent, so no existence leak.
- 2026-11-09. Outbox rows (created, archived, merged) carry ids only, never message text. Each carries a dedupe key. The store writes the row in the same call as the state change. Drizzle store must do this in one transaction.
- 2026-11-09. Summary cache: a stored summary is reused until 10 or more new non-internal messages arrive after summary_updated_at. force re-summarises. Only the newest 200 non-internal messages go to the model. Internal notes are excluded from the transcript. Reason: long conversations and staff notes.
- 2026-11-09. A fallback summary (model unavailable or a non-retryable provider error) is returned but never stored. On a provider error the last stored summary is returned first, if one exists.
- 2026-11-09. Delivery status is one record per message. Transitions use delivery-rules.ts. A second markFailed on a failed message keeps the first reason. Failure reasons must match a short code pattern (lowercase, digits, _ : . -, max 80 characters). Anything else is stored as unknown_failure. Reason: provider text may echo request data.
- 2026-11-09. Delivery writes use compare-and-set on the stored status. After 3 lost races it throws delivery_conflict.
- 2026-11-09. Change request for the chatbot_conversations table (owner of shared/schema.ts): add status (open, archived, merged), handler, merged_into_id (same company, composite FK), summary (text), summary_updated_at. Needed before any Drizzle store can run. Done: shared/schema.ts and migrations-draft/0055_conversation_store_columns.sql now carry these columns (updated 2026-11-09).
- 2026-11-09. Change request for db/ (runtime owner, db/runtime.ts is not in this area): add chatbot_message_deliveries with company_id, message_id, conversation_id, status, external_message_id, failure_reason, retry_count, updated_at; primary key (company_id, message_id); composite FK to chatbot_conversations. Also a draft SQL file in db/migrations-draft/ under the next number for this slice.
- 2026-11-09. No Drizzle DeliveryStatusStore was written. A Drizzle ConversationStore was added later (see the G1 section) (updated 2026-11-09). The delivery table does not exist yet. The db/harness folder now holds apply-drafts.mjs and pg-local.sh (updated 2026-11-09), but this entry records no real Postgres run.
- 2026-11-09. Scoped strict type check of the four runtime files passed (tsc, no full run). Test file: 21 tests, all passing; existing chatbot-runtime.test.mjs still 33 of 33.

## Drizzle conversation store, reply transaction, store events (G1, 2026-11-09)

- 2026-11-09. Drizzle store is in drizzle-conversation-store.ts. It implements every ConversationStore method, with company_id on every query. Builders are exported and rendered by drizzle-conversation-store.test.mjs. Reason: no database is available in the test harness.
- 2026-11-09. Assumed columns: chatbot_conversations now has status, handler, merged_into_id, summary, summary_updated_at, customer_id and external_thread_id in shared/schema.ts (updated 2026-11-09). The store imports chatbotConversations from shared/schema.ts and no longer declares a provisional local table (runtimeConversations) or ASSUMED columns (updated 2026-11-09). Reason: agent A's draft was not present when this was written. The shared table has replaced the provisional one (updated 2026-11-09).
- 2026-11-09. external_thread_id is stored in its own column. session_id (NOT NULL) takes it when set, or "rt-<id>" otherwise. Reason: the contract has no session field for channel conversations.
- 2026-11-09. Stored role: customer is written as user, because the chatbot_messages check allowed only user and assistant when this was written. It now allows user, assistant, staff and system (shared/schema.ts and migrations-draft/0055) (updated 2026-11-09). The change request to widen it is done (updated 2026-11-09).
- 2026-11-09. Reply transaction: insertReply runs one db.transaction. It writes the message row, bumps the conversation updated_at, and calls enqueueSend(tx), which writes the channel send row through the same tx. Any failure rolls all of it back. Reason: a crash cannot leave a stored reply with no send.
- 2026-11-09. Send key is "reply:<message id>", set by the writer, so a retry of one reply cannot send twice (channels/outbox.ts idempotency).
- 2026-11-09. Web conversations get no channel send. The writer sends only when buildSend returns a message. Reason: web chat has no provider to send to.
- 2026-11-09. passThroughLock: the writer takes a lock option. Default is createKeyedLock (in-process). Wording conflict: the task said to keep passThroughLock for the non-database deployment, but cart/ documents passThroughLock for the database deployment. Implemented as an injectable option, so either deployment can pass either lock. Owner to confirm the default for production.
- 2026-11-09. ReplyWriter type is narrowed to { message: { id }, accepted }. ChatbotService still satisfies it. Reason: the conversation-store writer does not return a chatbot-storage record.
- 2026-11-09. The conversation-store writer stores the text it is given. Generative-UI composition stays in ChatbotService.recordAssistantReply. Channel replies are plain text, so this is the right input for a send.
- 2026-11-09. Conversation events (chatbot.conversation.created, archived, merged) are published by store-events.ts after the store call returns, so only committed changes are published. The events processor relays only inbox topics (events/outbox.ts isInboxTopic), so there is no double publish.
- 2026-11-09. Voice idle end reason: voice/voice-service.ts already ends idle sessions with the reason "idle" (VOICE_END_REASONS). The PHP reference has no idle end reason, so no PHP name exists to match. No change made in voice/. The DB check constraint (db/voice.ts sessionEndReasonCheck and migrations-draft/0002_voice.sql) now allows idle, added 2026-11-09 (UNVERIFIED against Postgres.)
- 2026-11-09. Outbox: channels/outbox.ts was not changed. enqueue already takes the transaction handle. The channel outbox does not emit per-row sent or failed events, so there is nothing to wire to realtime yet. Change request if the owner wants delivery status pushed.
